## 2. `S36-R1`, `S36-R2` & `S37-R4` — `Bm25BatchScorer` Documentation, `S35-R1` Loop-Alignment Correction, and `build_score_table` Optimization (`d2c264c`, `9f6c03f`)

### 2.1 `S36-R1` & `S37-R4`: `Bm25BatchScorer` Rustdoc and `docs/review/c12.md` §6.2 Loop-Alignment Correction
- **Rustdoc (`d2c264c`)**:
  - Updated the struct rustdoc on `Bm25BatchScorer` (`src/scoring/bm25.rs:42-46`) and method rustdoc on `Bm25BatchScorer::new` (`src/scoring/bm25.rs:53-59`) to document that `Bm25BatchScorer` owns a 256-entry copy of `norm_table` with every caller entry `<= 0.0` or `NaN` clamped to `f32::MIN_POSITIVE`.
- **`S35-R1` Cause Correction (`S37-R4`, `docs/review/c12.md:262-267`)**:
  - Corrected `docs/review/c12.md` §6.2 in place: the `+14.8%` `score_loop` slowdown (`1.212 -> 1.391 ns/doc`) originally reported in `S35-R1` on the external integration-test probe (`/tmp/s33_probes/s33_bm25_bench.rs`) was a **loop-alignment artifact**, not an unhoisted `has_non_positive_norm` branch. At `beaa055` (`6acb313` code) the compiler had already unswitched the loop so the unguarded loop copy that ran was byte-identical to `f1f923e`'s, and at `ebeb81a` (with no change to `score()`) the external probe shifted back to `1.394–1.406 ns/doc`; compiling the same `ebeb81a` source with `-C llvm-args=-align-loops=32` gives `1.218 ns/doc` whereas `-C llvm-args=-align-loops=64` gives `1.394 ns/doc`.
  - The `a1bc151` (`S35-R1`) change is kept because storing an owned clamped `norm_table: [f32; 256]` is simpler, removes `has_non_positive_norm` and duplicate loop bodies, and is unconditionally `NaN`-safe for any table. To prevent 32B vs 64B loop-alignment bimodality across benchmark builds, `-C codegen-units=1 -C llvm-args=-align-loops=32` is pinned in `.cargo/config.toml` and `Makefile` (`BENCH_RUSTFLAGS`).

### 2.2 `S36-R2`: `FieldnormEncoder::build_norm_table` & `FieldnormEncoder::build_score_table` Optimization
- **Fix (`d2c264c`)**:
  - In `FieldnormEncoder::build_norm_table` (`src/scoring/fieldnorm.rs:129-144`), hoisted `inv_avg_dl = if avg_dl > 0.0 && (1.0 / avg_dl).is_finite() { 1.0 / avg_dl } else { 0.0 }` and `max_ratio = f32::MAX / k1.max(1.0)` outside the 256-iteration loop, replacing 256 floating-point divisions (`dl / avg_dl`) and per-entry `.is_finite()` checks with a single multiplication (`dl * inv_avg_dl`) and `.min(f32::MAX).max(f32::MIN_POSITIVE)` clamp.
  - In `FieldnormEncoder::build_score_table` (`src/scoring/fieldnorm.rs:161-180`), pre-allocated `vec![[0.0f32; 256]; max_tf as usize + 1]` and computed each row `tf >= 1` via a branch-free `row.iter_mut().zip(norm_table.iter())` loop (`*dst = numer / (tf_f + len_norm)`), which LLVM auto-vectorizes with `vdivps`.
- **Measured Performance (`search_and_scoring/fieldnorm_build_score_table`, `benches/core_bench.rs:4438-4465`)**:
  - `benches/baselines/bindiego/core_bench.json`: **`0.1698 ns/cell` min / `0.1705 ns/cell` median** under default `THP-off` (`0.1742 ns/cell` min / `0.1751 ns/cell` median at `df81570`), and **`0.1682 ns/cell` min / `0.1686 ns/cell` median** under `--thp-on` (reviewer external probe at `ebeb81a` measured **`-5.4%` by median** against `f1f923e`).

## 3. `E6`, `S37-R4` & `S38-R4` — Memory-Footprint Claims Asserted by Tests (`8c2ecd7`, `9f6c03f`, `304d5f9`)

`tests/memory_footprint_e6.rs` (`tests/memory_footprint_e6.rs:1-402`) contains 4 deterministic integration tests verifying crate memory-footprint claims without tautological `size_of` or `Vec::len` assertions:

1. **`test_e6_elias_fano_variants_bits_per_element_across_distributions`** (`tests/memory_footprint_e6.rs:29-171`):
   - Uniform-sparse (`n = 10,000`, `U = 10,000,000`): asserts `EliasFano::bits_per_element()` in `[11.5, 14.5]`, `PartitionedEliasFano` and `OptimalPartitionedEliasFano` in `[11.5, 15.5]`, `ClusteredEliasFano <= 16.0`.
   - Clustered/bursty (50 runs of 200 contiguous IDs separated by `100,000` gaps): asserts `OptimalPartitionedEliasFano < PartitionedEliasFano < EliasFano` and `OptimalPartitionedEliasFano <= 4.5 bits/elem` (`5.4202 bits/elem` measured on Zipf-clustered `n = 100,000` in `core_bench.json`).
   - Fully-dense (`0..100_000`): asserts `ClusteredEliasFano::bits_per_element()` in `[2.50, 2.55]` (`2.5146 bits/elem` measured in `core_bench.json`) and `HybridPostingList::encoding() == PostingEncoding::Clustered`.
   - Run-heavy (`n = 10,000`, 512-ID runs separated by 64-ID gaps): asserts `ClusteredEliasFano <= 3.0 bits/elem` and `< OptimalPartitionedEliasFano`.
2. **`test_e6_tries_bytes_per_state_and_bytes_per_key`** (`tests/memory_footprint_e6.rs:174-235`):
   - `DoubleArrayTrie`: asserts `dat.mem_size() == dat.total_states() * 12` (`8 B` `DaState` + `4 B` `NInfo`).
   - `DoubleArrayTrieMap<u32>` vs `DoubleArrayTrieMap<u64>`: builds both maps on the same 2,000 keys, calls `shrink_to_fit()`, and asserts `dat_map.total_states() == dat_map_u64.total_states()`, `u64_value_bytes == u32_value_bytes * 2` (`dat_map.mem_size() - dat_map.total_states() * 12` uses half the value-table bytes of 8-byte slots), and `12.0..=16.0 B/state` total.
   - `CsppTrie`: asserts active `bytes/key` (`(stat.used_size - stat.frag_size) / num_words`) in `[7.0, 14.5]` on 10,000 shared-prefix keys (`9.6011 B/key` measured on `1,000,000` shared-prefix keys in `core_bench.json`).
3. **`test_e6_fieldnorm_encoder_one_byte_per_doc_and_quantization_bounds`** (`tests/memory_footprint_e6.rs:238-313`):
   - Asserts `FieldnormEncoder::encode(0) == 0`, `FieldnormEncoder::encode(u32::MAX) == 239`, `FieldnormEncoder::decode(239) == 15u32 << 28`, `size_of_val(doc_lengths.as_slice()) == size_of_val(fieldnorm_bytes.as_slice()) * 4` (`4.0x` smaller than raw `u32` lengths), `< uint_vec.mem_size()` vs `UintVecMin0` (`1.125 B/doc` for 9-bit document lengths), `size_of_val(&norm_table) == 1024`, and verifies across all `100,000` documents plus `0..=15` and `16..2^31` that `decoded <= dl`, `(dl - decoded) / dl <= 0.125`, `quantization_error(dl) == (dl - decoded) / dl`, and for every `b < 255` the next code `FieldnormEncoder::decode(b + 1) > dl` strictly brackets `dl` (so a broken constant-`0` encoder is caught immediately).
4. **`test_e6_rank_select_space_overhead_percent_and_mem_size`** (`tests/memory_footprint_e6.rs:316-402`):
   - On 1 Mbit (`1,048,576` bits = `131,072` bytes): asserts `Rank9` in `[25.0%, 25.1%]`, `RankSelectSE256` rank-only in `[25.0%, 25.1%]` and with `sel0+sel1` in `[37.4%, 37.7%]`, `RankSelectSE512_64` rank-only in `[18.7%, 18.8%]` and with `sel0+sel1` in `[25.0%, 25.1%]`, `RankSelectInterleaved256` rank-only `== 100.0%` and with select cache in `[103.0%, 103.5%]`, `RankSelectSimple` in `[12.5%, 12.6%]`, and `RankSelectFewOne` `< 5.0%` on `0.1%` sparse 1 Mbit.

### 4.2 `B3`, `S38-R1..R2`, `S39-R4` & `S40-R1` Shared-Host-Resilient Regression Gate (`scripts/bench_compare.py`, `Makefile`, `benches/core_bench.rs`)
- **Pinned Loop Alignment & Build Metadata (`build.rs`, `Makefile:101-105`)**:
  - `-C codegen-units=1 -C llvm-args=-align-loops=32` is pinned in `.cargo/config.toml` and `BENCH_RUSTFLAGS` in `Makefile`, and exported via `ZIPORA_BUILD_RUSTFLAGS` in `build.rs`.
- **Self-Only Process Calls & Quietest-CCD Self-Repinning (`S38-R1`, `S39-R4`, `S40-R1`, `benches/core_bench.rs:84-740`, `benches/e2e_search_bench.rs:276-316`)**:
  - Neither benchmark binary touches any other process or thread on the host. The only OS calls act on the benchmark process itself: pinning the current thread (`sched_setaffinity(0, ...)`) to `select_primary_core` (`ZIPORA_BENCH_PIN_CORE` / `ZIPORA_BENCH_CORE` override if set, or core 23 on >=24-core hosts, else `logical_cores - 1`) and disabling transparent hugepages for the current process (`prctl(PR_SET_THP_DISABLE, 1, 0, 0, 0)`) unless `--thp-on` or `ZIPORA_BENCH_THP=on` is passed.

- **Option B Shared-Host Confirm-on-Retry Gate (`S40-R1`, `scripts/bench_compare.py:1-600`, `Makefile:118-137`, `cf62b26`)**:
  - **Missing baseline or missing benchmark / `dataset_size` mismatch fails immediately** (`scripts/bench_compare.py:53-64`, `228-260`): structural/integrity failures never retry and exit `1` immediately.
  - **Per-benchmark thresholds stay at `5.0%` / `9.0%` (`min_ns_per_op`)**: when `--confirm-retries K` (`--confirm-retries 5` for `make bench_core` and `--confirm-retries 3` for `make bench_e2e_search` in `Makefile` when `UPDATE_BASELINE` is unset) is active and one or more benchmarks exceed their threshold on the initial full-suite pass, `scripts/bench_compare.py` waits for a quiet host window (`wait_for_quiet_host_window`, checking `/proc/loadavg` `nr_running <= 6` and `/proc/stat` `busy_cores <= 6.5`) and re-runs each failing benchmark in an isolated `--filter <bench_name>` process (`run_isolated_retry`, `scripts/bench_compare.py:152-204`) up to `K` times, failing (`exit 1`) only if a regression persists across every retry.
  - **Effective Detection Sensitivity Disclosure (`S41-R1`)**:
    - Because `--confirm-retries 5` passes a benchmark if **any** of up to `1 + 5 = 6` attempts (`1` initial full-suite pass + up to `5` isolated `--filter` retries) falls within the `+9.0%` (`min_ns_per_op`) threshold, taking the minimum across 6 attempts compresses the measured delta relative to a single-run mean/min by ~`2–3%` on DRAM-bandwidth-bound benchmarks with natural shared-host run-to-run variance (`~2–4%`).

Tight-loop CPU-bound benchmarks with `5.0%` thresholds and `< 0.5%` run-to-run spread remain sensitive down to ~`+5.5%`.

### 4.3 `S39-R2` & `S40-R2` — Multi-Run Measurement of Transparent Hugepages (`THP-Off` vs `--thp-on` Across 3 Runs + `/proc/buddyinfo` Free `2 MiB` Block Counts)

By default, `benches/core_bench.rs` and `benches/e2e_search_bench.rs` call `prctl(PR_SET_THP_DISABLE, 1, 0, 0, 0)` on their own process so that multi-megabyte working sets are backed deterministically by `4 KiB` pages rather than variable partial `2 MiB` THP promotions across runs when host physical memory is fragmented. Passing `--thp-on` (or `ZIPORA_BENCH_THP=on`, or running `python3 scripts/measure_thp_impact.py`) skips `PR_SET_THP_DISABLE` and measures the impact of kernel Transparent Hugepages (`transparent_hugepage/enabled = [always]`, `defrag = [madvise]` on `bindiego`):

- **Why `--thp-on` Depends on `/proc/buddyinfo` Contiguous `2 MiB` (`order 9`) / `4 MiB` (`order 10`) Free Blocks (`S40-R2`)**:
  - On `bindiego`, `/sys/kernel/mm/transparent_hugepage/defrag` is `[madvise]` (not `always`), so standard anonymous `Vec` allocations without explicit `madvise(MADV_HUGEPAGE)` receive `2 MiB` THP pages **only** when the kernel buddy allocator has free contiguous `order 9` (`2 MiB`) or `order 10` (`4 MiB`) blocks in `Node 0, zone Normal` (`/proc/buddyinfo`) without synchronous compaction:
    - **Fragmented host state (e.g. immediately after heavy multi-process builds)**: `/proc/buddyinfo` was observed at:
      `Node 0, zone Normal 267942 185939 91736 86415 69851 53437 34818 22259 10802 10 0`
      (`10` free `order 9` blocks and `0` free `order 10` blocks = only **`20 MiB`** of `2 MiB` hugepages across the entire host!). In that state, `--thp-on` cannot back a `125 MiB` `Rank9` bitvector or `400+ MiB` `KeyValueRadixSort` arena with `2 MiB` hugepages and falls back to `4 KiB` pages (`~44.4 ns/op` on `rank9/rank1` and `~206.6 ns/elem` on `radix_sort/kv_u64_u64`, matching `THP-off`).

- **Corpus & Queries** (`benches/e2e_search_bench.rs:497-694`, fixed seed `SEED_E2E: u64 = 0x5A17_0E11_E2E5_EA2C` at line 40):

### 5.3 Space, Tail-Latency (`p99`), and `S39-R2` Uncompressed Baseline Cause Disclosure
- **Space Breakdown (`S38-R3` / `S39-R3`)**:
  - **Postings-vs-postings is parity**: `Zipora` `HybridPostingList` uses **`1.2232 B/posting`** (`1,921,100` B) vs `Tantivy v0.26.2` postings at **`1.2269 B/posting`** (`1,926,930` B, `0.3%` difference).

- **Why `UncompressedBaselineEngine` Moved from `11,346 QPS` (`088b065`) to `8,548.15 QPS` (`f2a4a45`) (`S39-R2`)**:
  - As shown in §5.2 above, toggling `PR_SET_THP_DISABLE` (`THP-off` vs `--thp-on`) changes `UncompressedBaselineEngine` by only **`+0.03%`** (`8,548.15 q/s` vs `8,545.41 q/s`), `Zipora BMW` by **`+0.29%`** (`19,792.61 q/s` vs `19,734.93 q/s`), and `Tantivy v0.26.2` by **`+0.54%`** (`12,152.85 q/s` vs `12,088.14 q/s`).
  - The shift in `UncompressedBaselineEngine` from `88,135 ns/q` (`11,346 QPS` in `088b065`) to `116,984.4 ns/q` (`8,548.15 QPS` in `f2a4a45` / `117,663 ns/q` in `df81570`) came from removing the custom `madvise(MADV_HUGEPAGE)` 192 MiB `brk` arena prewarmer in `07c6ac2` (`S38-R2`). `UncompressedBaselineEngine` allocates `4,096` separate `Vec<u32>` and `4,096` separate `Vec<u16>` buffers (averaging ~1.5 KiB each); without an explicit `madvise(MADV_HUGEPAGE)` across the `brk` heap, the host's `transparent_hugepage/defrag = [madvise]` policy does not promote those small heap allocations to `2 MiB` THP pages.

## 6. `S39-R5` (`IntVec::get_delta` $O(1)$ Checkpoints) & `S39-R6` (Test-Suite Speed-Ups)

### 6.1 `S39-R5` — `IntVec::get_delta` Bounded to $O(1)$ via Sampled Prefix Checkpoints (`b6fe54a`)
- **Defect (`src/containers/specialized/int_vec.rs:1159-1194` at `304d5f9`)**:
  - For non-uniform `CompressionStrategy::Delta { base_value, delta_bits }`, `IntVec::get_delta` reconstructed `values[index]` by summing every delta from `1..=index` on every call ($O(\text{index})$ per lookup, making $N$ random/sequential lookups $O(N^2)$). In `test_simd_edge_cases`, 100,000 `.get(i)` calls executed ~5 billion `read_bits` iterations (`47.36s` in release). In addition, `analyze_delta` did not call `Self::detect_uniform_delta(values)` before returning `CompressionStrategy::Delta`.
- **Fix & Storage Disclosure (`src/containers/specialized/int_vec.rs:756-1240`, `b6fe54a`)**:
  - `analyze_delta` (`src/containers/specialized/int_vec.rs:758-765`) now checks `Self::detect_uniform_delta(values)` first so arithmetic progressions select `UniformDelta` ($O(1)$ multiplication with zero index bytes).
  - For non-uniform `CompressionStrategy::Delta { base_value, delta_bits }`, `compress_delta` (`src/containers/specialized/int_vec.rs:954-1008`) populates `self.index: Option<Box<[u8]>>` with an 8-byte little-endian `u64` prefix-sum checkpoint every `DELTA_SAMPLE_STRIDE = 64` elements (`sample_idx = 1..=num_samples`, storing `values[sample_idx * 64]`).
  - **Storage change disclosure**: `self.index` adds `floor((len - 1) / 64) * 8` bytes = **`1.0 bit/element`** (`0.125 B/elem`) for non-uniform `Delta` vectors with `len > 64` (`0` bytes for `len <= 64`), accounted for in both `estimate_compression_ratio` (`src/containers/specialized/int_vec.rs:869-875`) and `IntVec::memory_usage()`.
  - `get_delta` (`src/containers/specialized/int_vec.rs:1194-1238`) jumps directly to `sample_idx = index / 64` in `self.index` and sums at most `DELTA_SAMPLE_STRIDE - 1 = 63` deltas.
- **RED Timing Test (`test_s39_r5_non_uniform_delta_get_is_bounded_o1`, `src/containers/specialized/int_vec.rs:1609-1639`)**:
  - Fails on `304d5f9` (`5,000` tail `.get()` calls on a `50,000`-element non-uniform `Delta` vector took `884.49ms > 250ms` budget); passes at `b6fe54a` in `< 1ms`. Release `int_vec` test suite (`16` tests) dropped from **`47.36s` to `0.09s`**.
