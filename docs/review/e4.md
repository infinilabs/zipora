## 3. Phase E (`E4`) Optimization Leads (`E4(a)..(g)` & `E3.1..E3.10`) — Root Cause, Implementation, & Measured Gains

### 3.1 `E4(g)` — Smart-Pointer & Primitive Slice Serialization (`44ee835`)
- **Files**: `src/io/smart_ptr.rs`, `src/io/data_output.rs`, `benches/s23_serialization_bench.rs`
- **Root Cause**: `register_active_ser_ptr` probed `SerializationContext` twice (`has_seen` + `get_or_assign_id`) using default `RandomState` SipHash-1-3 (`HashMap<usize, u32>`) and boxed `Box<dyn Any>` on every unique `Rc<T>` / `Arc<T>` via `retain_object`; `Vec<T>` serialized element-by-element through per-element `T::serialize` calls even on little-endian `Pod` primitives (`u8..u64`, `i8..i64`).
- **Optimization**: Added multiplicative identity hashing (`PtrHasher`, `PtrBuildHasher`), a single-probe `SerializationContext::register_or_assign_id` (`Entry`), a lazy `retain_fn: impl FnOnce() -> P` closure in `register_active_ser_ptr`, type-homogeneous `retained_primary: Option<Box<dyn Any>>` (`Box<Vec<P>>`) in `SerializationContext::retain_object` (cleared on `SerializationContext::clear` [`S48-R9`]) to avoid per-pointer heap allocations, and `SerializableType::serialize_slice` (`bytemuck::cast_slice` bulk writes via `DataOutput::write_bytes` in `Vec<T>::serialize` for little-endian `u8..u64` and `i8..i64` on `cfg(target_endian = "little")`, matching `DataOutput::write_u16`, `DataOutput::write_u32`, and `DataOutput::write_u64`'s documented little-endian contract).
- **Measured Result (`benches/s23_serialization_bench.rs`)**:
  - `Vec<Rc<u64>>` (100k) serialize (`vec_rc_u64_100k_ser`): `130.90–137.94 ns/elem -> 23.65–24.25 ns/elem` min / `25.02–26.91 ns/elem` med (**`5.40x–5.83x` faster / `-81.5%` to `-82.9%`** vs `b4148fc`, **`1.90x` faster / `-47.3%`** vs pre-C9 `46 ns/elem`).
  - `Vec<Vec<u32>>` (`1,000 x 100`, `vec_vec_u32_1000x100_ser`) serialize: `245.50–247.26 ns -> 14.54–15.07 ns/inner Vec` (**`16.41x–16.88x` faster / `-93.9%` to `-94.1%`** vs `b4148fc`, **`4.31x–4.47x` faster / `-76.8%` to `-77.6%`** vs pre-C9 `65 ns/inner Vec`).
  - `Vec<Box<u64>>` (100k) deserialize: `29.89 ns/elem`; `Vec<u64>` (1M) deserialize: `0.967 ns/elem`.

### 3.2 `E4` / `E3.1` — `RankSelectInterleaved256` Unpadded 40-Byte `InterleavedLine` & `select0_cache` (`7dd5bd9`)
- **Files**: `src/succinct/rank_select/interleaved.rs`, `tests/memory_footprint_e6.rs`, `scripts/gate_baseline.txt`
- **Root Cause**: `#[repr(C, align(32))]` on the 40-byte `InterleavedLine` (`rlev1: u32, rlev2: [u8; 4], bit64: [u64; 4]`) padded every 256-bit block to `64` bytes (`24` dead padding bytes per line = `+75%` of raw bitvector wasted), and `RankSelectInterleaved256` had no `select0` sample table (`select0` binary-searched all `3,906,250` lines).
- **Optimization**: Replaced `#[repr(C, align(32))]` with unpadded 8-byte-aligned `#[repr(C)]` (`size_of::<InterleavedLine>() == 40`, asserted at compile time) and added `select0_cache: Option<FastVec<u32>>` (storing 32-bit `line_idx` indices in both `select_cache` and `select0_cache`, supporting bitvectors up to $2^{40}$ bits = `1 Terabit` [`S47-R7`]) to narrow `select0` binary search to a narrow L1-resident line window.
- **Measured Result**:
  - `RankSelectInterleaved256` space overhead (`space_overhead_percent()` / `rank_select/interleaved256_overhead_pct` [`S48-R7`]):
    - **Rank-only (`select_cache: None, select0_cache: None`)**: **`100.00% -> 25.00%` overhead** (`40 B / 32 B - 1`, `-75.00` percentage points; total footprint `200.00% -> 125.00%` of raw bitvector, asserted in `tests/memory_footprint_e6.rs`).
    - **With `select1` + `select0` caches (`select_cache` + `select0_cache`)**: **`103.1249% -> 31.2500%` overhead** (`-71.87` percentage points; total footprint `203.12% -> 131.25%` of raw bitvector, recorded in `rank_select/interleaved256_overhead_pct` in `competitor_bench.json` and asserted in `tests/memory_footprint_e6.rs`; compare `RankSelectSE256` at `25.00%` rank-only / `37.50%` with `sel1+sel0` caches in `rank_select/se256_overhead_pct`).
  - `rank_select/interleaved256/select0`: **`651.87 ns/op -> 151.37 ns/op`** (**`4.31x` faster / `-76.8%`**).
  - Flips `rank_select/interleaved256/rank1` vs `sucds::Rank9Sel` to **`LEADING`** (`35.027` vs `43.334 ns/op`, `-0.00% <= +10.0%` secondary space).

### 3.3 `E4` / `E3.2` — Exact Bit-Offset `select1` / `select0` Samples & Rank-Free `next_geq` in `EliasFano` (`b6cbccc`)
- **Files**: `src/succinct/elias_fano/basic.rs`
- **Root Cause**: `EliasFano::build_samples` stored word-aligned bit indices `(word_idx * 64)` in `select1_samples` and `select0_samples`, forcing `select1`/`select0` to load a second cache line (`rank_samples[start_word / 8]`) and popcount up to 7 preceding words; `next_geq` called `rank1(pos)` + `get(idx)` (a redundant `select1`).
- **Optimization**: Stored the exact bit offset `(word_idx * 64 + select_in_word(...))` in `select1_samples` (`SELECT1_SAMPLE_RATE = 128`) and `select0_samples` (`0` extra bytes, eliminating the `rank_samples` load and popcount pre-loop), added `EliasFanoWire` (`#[serde(into = "EliasFanoWire", from = "EliasFanoWire")]`) to preserve 100% bidirectional JSON and `bincode` wire compatibility with pre-`b6cbccc` payloads while clamping forged `wire.len` against `high_bits` popcount and `low_bits` capacity and rebuilding exact-bit-offset samples on deserialization (`S47-R5`, `S48-R9`), and rewrote `next_geq` to scan forward directly from `select0(target_high - 1) + 1` while tracking `idx = bit_pos - target_high` without calling `rank1` or `select1`.
- **Measured Result**:
  - `elias_fano/uniform/ef_select`: **`28.021 -> 17.968 ns/op`** (**`1.56x` faster / `-35.9%`**).
  - `elias_fano/zipf_clustered/ef_select`: **`28.774 -> 19.500 ns/op`** (**`1.48x` faster / `-32.2%`**).
  - `elias_fano/dense/ef_select`: **`17.802 -> 14.382 ns/op`** (**`1.24x` faster / `-19.2%`**).
  - `elias_fano/{uniform,zipf_clustered,dense}/ef_next_geq` (`core_bench`): `34.76 -> 22.27`, `39.59 -> 30.57`, `25.85 -> 14.77 ns/op` (**`-24.4%` to `-44.3%` faster**), flipping `elias_fano/dense/ef_next_geq` vs `sucds::EliasFano` to **`LEADING`**.

### 3.4 `E4(e)` / `E3.3` — Top-Down Bulk `DoubleArrayTrie::build_from_sorted` & $O(\text{degree})$ `ZiporaTrie` Child Links (`21d6e06`)
- **Files**: `src/fsa/double_array/trie.rs`, `src/fsa/zipora_trie/{builder,search,storage,trie}.rs`
- **Root Cause**: `DoubleArrayTrie::build_from_sorted` called incremental `trie.insert(key)` in a loop, triggering repeated `relocate(curr, ch)` moves whenever a node gained a new child byte, and `find_free_base` scanned `states` linearly from `base = 1`. Similarly, `ZiporaTrie` (`TrieStorage::DoubleArray`) scanned all 256 possible labels on every `relocate_state` and `update_grandchildren_check_values`.
- **Optimization**: Replaced the incremental `insert` loop in `DoubleArrayTrie::build_from_sorted` with a direct top-down explicit-stack range partitioner (`Frame { lo, hi, depth, parent_state }`) over sorted slices (with galloping child-range scan, a single-key unary-suffix fast path, and `find_free_base` free-slot `pos ^ ch0` scanning with `search_head`) that allocates `base` once per internal node with **zero `relocate` calls** and $O(1)$ call-stack usage (`S47-R11`); added `child_links: FastVec<u32>` (`da_link_child`) to `TrieStorage::DoubleArray` in `ZiporaTrie` so `relocate_state` and `update_grandchildren_check_values` walk actual children in $O(\text{out-degree})$ (trading `+4 B/state` = `12 B/state` in `ZiporaTrie`, accounted in `ZiporaTrie::memory_usage()` and `memory_stats()`, while standalone `DoubleArrayTrie` remains `8 B/state`).
- **Measured Result**:

- **Root Cause**:
  - `E3.9`: `SuffixArrayBuilder::build_sequential` scanned all `10,000,000` bytes twice in `select_algorithm` before calling `sais_construct`, which copied `&[u8]` into an `80 MB` `Vec<usize>` and allocated `Vec<bool>` arrays on every recursive level; `SuffixArray::search_range` ran two unconditional `[0, n)` binary searches even when `lower_bound` missed.

- **Optimization**:
  - `E3.9`: Removed the redundant `analyze_text_characteristics` pre-scans, specialized top-level `sais_core_bytes` / `sais_induce_bytes` / `sais_lms_substr_eq_bytes` on `&[u8]` and recursive `sais_core` / `sais_induce` on `u32` slices with packed 64-bit word bitvectors (`WordBitVec`) instead of `Vec<bool>`, added a 2-byte prefix bounds lookup table (`Bucket2Table`, `bucket2: Option<Box<[(u32, u32)]>>`, `512 KiB`, included in `stats.memory_used` and read directly via `built.stats().memory_used` in `suffix_array/zipora_bytes_per_byte` = `9.0524 B/byte` at `10M` bytes alongside `8 B` `usize` SA entries + `1 B` text [`S47-R11`, `S48-R9`]) to narrow `lower_bound_in` to the matching 2-byte bucket, and rewrote `SuffixArray::search_range` to return `(lower, lower)` immediately on a miss and gallop (`step = 1, 2, 4, ...`) from `lower` to `upper` on a hit.
