## 3. Phase E (`E4`) Optimization Leads (`E4(a)..(g)` & `E3.1..E3.10`) — Root Cause, Implementation, & Measured Gains

### 3.1 `E4(g)` — Smart-Pointer & Primitive Slice Serialization (`44ee835`)
- **Files**: `src/io/smart_ptr.rs`, `src/io/complex_types.rs`, `src/io/data_output.rs`, `src/io/data_input.rs`
- **Root Cause**: `SerializationContext::register_rc_ptr` / `register_arc_ptr` hashed every pointer in a `HashMap<usize, u32>` and boxed a closure on every unique `Rc<T>` / `Arc<T>`; `Vec<T>` / `VecDeque<T>` serialized element-by-element through virtual `Write` calls even on little-endian `Pod` primitives (`u8..u64`, `i8..i64`, `f32`, `f64`).
- **Optimization**: Added a direct-mapped 1,024-entry pointer-identity cache + contiguous `keep_alive` slab in `SerializationContext` (with thread-local context reuse in `serialize_to_vec` / `deserialize_from_slice`), and specialized bulk little-endian slice read/write for primitive `Pod` types (`SerializableType::write_slice_le` / `read_slice_le`).
- **Measured Result (`benches/s23_serialization_bench.rs`)**:
  - `Vec<Rc<u64>>` (100k) serialize: `105.0 ns/elem -> 24.25 ns/elem` min / `25.02 ns/elem` est (**`4.20x` faster / `-76.2%`** vs `b4148fc`, **`1.84x` faster / `-45.6%`** vs pre-C9 `46 ns/elem`).
  - `Vec<Vec<u32>>` (10k x 16) serialize: `73.79 ns -> 14.54 ns/inner Vec` (**`5.08x` faster / `-80.3%`** vs `b4148fc`, **`4.47x` faster / `-77.6%`** vs pre-C9 `65 ns/inner Vec`).
  - `Vec<Box<u64>>` (100k) deserialize: `29.89 ns/elem`; `Vec<u64>` (1M) deserialize: `0.967 ns/elem`.

### 3.2 `E4` / `E3.1` — `RankSelectInterleaved256` Unpadded 40-Byte `InterleavedLine` & `select0_cache` (`7dd5bd9`)
- **Files**: `src/succinct/rank_select/interleaved.rs`, `tests/memory_footprint_e6.rs`
- **Root Cause**: `#[repr(C, align(32))]` on the 40-byte `InterleavedLine` (`rlev1: u32, rlev2: [u8; 4], bit64: [u64; 4]`) padded every 256-bit block to `64` bytes (`24` dead padding bytes per line = `+75%` of raw bitvector wasted), and `RankSelectInterleaved256` had no `select0` sample table (`select0` binary-searched all `3,906,250` lines).
- **Optimization**: Replaced `#[repr(C, align(32))]` with unpadded 8-byte-aligned `#[repr(C)]` (`size_of::<InterleavedLine>() == 40`, asserted at compile time) and added `select0_cache: Option<FastVec<u32>>` narrows `select0` binary search to a narrow L1-resident line window.
- **Measured Result**:
  - `RankSelectInterleaved256` space overhead (`rank_select/interleaved256_overhead_pct`): **`103.1249% -> 31.2500%`** (`-65.62` percentage points, total footprint `203.13% -> 137.50%` of raw bitvector).
  - `rank_select/interleaved256/select0`: **`651.87 ns/op -> 155.71 ns/op`** (**`4.19x` faster / `-76.1%`**).
  - Flips `rank_select/interleaved256/rank1` vs `sucds::Rank9Sel` to **`LEADING`** (`34.877` vs `44.434 ns/op`, `+8.64% <= +10.0%` secondary space).

### 3.3 `E4` / `E3.2` — Exact Bit-Offset `select1` / `select0` Samples & Rank-Free `next_geq` in `EliasFano` (`b6cbccc`)
- **Files**: `src/succinct/elias_fano/basic.rs`
- **Root Cause**: `EliasFano::build_samples` stored word-aligned bit indices `(word_idx * 64)` in `select1_samples` and `select0_samples`, forcing `select1`/`select0` to load a second cache line (`rank_samples[start_word / 8]`) and popcount up to 7 preceding words; `next_geq` called `rank1(pos)` + `get(idx)` (a redundant `select1`).
- **Optimization**: Stored the exact bit offset `(word_idx * 64 + select_in_word(...))` in `select1_samples` and `select0_samples` (`0` extra bytes, eliminating the `rank_samples` load and popcount pre-loop) and fused `next_geq` to scan forward directly from `select0(target_high - 1) + 1` while tracking `idx = bit_pos - target_high` without calling `rank1` or `select1`.
- **Measured Result**:
  - `elias_fano/uniform/ef_select`: **`28.021 -> 17.578 ns/op`** (**`1.59x` faster / `-37.3%`**).
  - `elias_fano/zipf_clustered/ef_select`: **`28.774 -> 19.132 ns/op`** (**`1.50x` faster / `-33.5%`**).
  - `elias_fano/dense/ef_select`: **`17.802 -> 14.059 ns/op`** (**`1.27x` faster / `-21.0%`**).
  - `elias_fano/{uniform,zipf_clustered,dense}/ef_next_geq` (`core_bench`): `34.76 -> 22.31`, `39.59 -> 29.86`, `25.85 -> 14.57 ns/op` (**`-26.1%` to `-40.4%` faster**), flipping `elias_fano/dense/ef_next_geq` vs `vers_vecs::EliasFanoVec` to **`LEADING`**.

### 3.4 `E4(e)` / `E3.3` — Top-Down Bulk `DoubleArrayTrie::build_from_sorted` & $O(	ext{degree})$ `ZiporaTrie` Child Links (`21d6e06`)
- **Files**: `src/fsa/double_array/trie.rs`, `src/fsa/traits.rs`
- **Root Cause**: `DoubleArrayTrie::build_from_sorted` called incremental `trie.insert(key)` in a loop, triggering repeated `relocate(curr, ch)` moves whenever a node gained a new child byte, and `find_free_base` scanned `states` linearly without a 64-bit occupancy bitmap. Similarly, `ZiporaTrie` (DoubleArray strategy) scanned all 256 possible labels on every `relocate` and `find_child`.
- **Optimization**: Replaced the incremental `insert` loop in `DoubleArrayTrie::build_from_sorted` with a direct top-down recursive range partitioner over sorted slices that collects all distinct outgoing bytes at `depth` in one pass and allocates `base` once per internal node with **zero `relocate` calls**, backed by an `occupied_bits: Vec<u64>` bitmap (`(!word).trailing_zeros()`) and `free_cursor` hint; added `first_child`/`next_sibling` links to `ZiporaTrie::DoubleArrayImpl`.
- **Measured Result**:
  - `tries/dat/url_paths/build_sorted`: **`326.32 -> 103.68 ns/key`** (**`3.15x` faster / `-68.2%`**) — beats `fst` (`348.39`), `qp_trie` (`131.68`), and `radix_trie` (`240.79`).
  - `tries/dat/random_16b/build_sorted`: **`269.25 -> 218.95 ns/key`** (**`1.23x` faster / `-18.7%`**) — beats `fst` (`1295.25`), `qp_trie` (`135.56`), and `radix_trie` (`230.58`).
  - `tries/dat/shared_prefix/build_sorted`: **`196.43 -> 59.75 ns/key`** (**`3.29x` faster / `-69.6%`**) — beats `fst` (`91.91`), `qp_trie` (`132.45`), and `radix_trie` (`203.52`).
  - `tries/zipora_trie_da/{build,lookup}` (`core_bench`): build **`1280.89 -> 559.57 ns/key`** (**`2.29x` faster**), lookup **`826.04 -> 738.11 ns/op`** (**`1.12x` faster**).

### 3.5 `E4(b)` / `E3.4` — SwissTable 16-Way SSE2 Group Probing & `17 B/slot` Layout in `ZiporaHashMap` (`f1cd7c0`)
- **Files**: `src/hash_map/storage.rs`, `src/hash_map/zipora_hash_map.rs`, `src/hash_map/gold_hash_map.rs`
- **Root Cause**: `HashEntry<K, V>` stored `{ key: Option<K>, value: Option<V>, hash: u64, _next: Option<u32> }` (`40 B/slot` for `(u64, u64)` = `83.89 B/entry` at `2^21` slots, `+135.29%` space overhead vs `hashbrown` & `std`) and probed 1 slot at a time in scalar code.
- **Optimization**: Replaced `HashEntry<K, V>` with a SwissTable control-byte array (`ctrl: Vec<u8>` with 16-byte mirrored sentinel tail, storing `CTRL_EMPTY = 0x80`, `CTRL_DELETED = 0xFE`, or 7-bit `h2 = (hash >> 57) as u8 & 0x7F`, probed 16 slots at a time via SSE2 `_mm_cmpeq_epi8` + `_mm_movemask_epi8`) paired with a flat `MaybeUninit<(K, V)>` slot buffer (`17 B/slot` for `(u64, u64)` = **`35.65 B/entry`**, `-4.63%` vs `hashbrown` & `std` `35.65 B/entry`), folded `AHash`/`FastHash` `u64` and `[u8; 16]` directly via 128-bit multiply-fold, and added power-of-two mask fast paths in `GoldHashMap`.
- **Measured Result (`competitor_bench`)**:
  - `hash_maps/zipora_hash_map/insert_u64`: **`109.067 -> 44.758 ns/op`** (**`2.44x` faster**), space **`83.89 -> 35.65 B/entry` (`0.00%` delta vs `hashbrown` & `std`)**.
  - `hash_maps/zipora_hash_map/get_u64`: **`71.362 -> 61.343 ns/op`**, space **`83.89 -> 35.65 B/entry` (`0.00%` delta vs `hashbrown` & `std`)** -> **`LEADING` vs `std::collections::HashMap`**.
  - `hash_maps/zipora_hash_map/insert_str16`: **`195.077 -> 53.680 ns/op`** (**`3.63x` faster**), space **`100.66 -> 52.43 B/entry` (`0.00%` delta vs `hashbrown`, `-50.00%` vs `std`)**.
  - `hash_maps/zipora_hash_map/get_str16`: **`179.555 -> 92.300 ns/op`**, space **`100.66 -> 52.43 B/entry` (`0.00%` delta vs `hashbrown`, `-50.00%` vs `std`)** -> **`LEADING` vs BOTH `hashbrown+ahash` and `std::collections::HashMap`**.
  - Flips **`3/16` `hash_maps` rows to `LEADING`** (up from `0/16 LEADING`).

### 3.6 `E4(f)` / `E3.5` — $O(1)$ Size-Class LUT & Per-Thread Magazine in `LockFreeMemoryPool` (`48d5a5a`)
- **Files**: `src/memory/lockfree_pool.rs`
- **Root Cause**: Every `allocate(256)` + `deallocate(ptr, 256)` pair scanned `SIZE_CLASSES` linearly and executed 4 atomic RMW `lock` operations (`2 x lock cmpxchgq` on `bin.head` + `2 x lock xaddq` on `bin.count`, plus atomic stats).
- **Optimization**: Added an $O(1)$ `size_to_bin` lookup table (exact `usize::trailing_zeros` for powers of two `64..=65536` and a 64-byte granulized LUT for `<= 4096`) and a per-thread magazine (`TLS_MAGAZINES`, caching up to `32` block offsets per bin for the active `pool_id` and flushing back to the global ABA-tagged Treiber stack on overflow, pool switch, `reset()`, or `Drop`).
- **Measured Result**:
  - `memory_pools/lockfree_pool/alloc_free_1t`: **`24.003 -> 5.669 ns/op`** (**`4.23x` faster / `-76.4%`**) — **`LEADING` vs `mimalloc`, `tikv_jemallocator::Jemalloc`, and `std::alloc::System` (`3/3 LEADING` on 1T)**!
  - `memory_pools/lockfree_pool/alloc_free_4t`: **`21.853 -> 5.677 ns/op`** (**`3.85x` faster / `-74.0%`**) — **`LEADING` vs `mimalloc`, `tikv_jemallocator::Jemalloc`, and `std::alloc::System` (`3/3 LEADING` on 4T)**!
  - Flips **`6/12` `memory_pools` comparisons to `LEADING`** (up from `0/12 LEADING`, and **`6/6 = 100.0% LEADING` for `LockFreeMemoryPool`**).

### 3.7 `E4(c)` + `E4(d)` / `E3.6` — Flat Huffman Decode LUTs, 64-Bit Bit-Flush, 4-State Lockstep `rANS64`, & Fast FSE LUT (`e673660`)
- **Files**: `src/entropy/huffman/encoder.rs`, `src/entropy/huffman/interleaved.rs`, `src/entropy/rans.rs`, `src/entropy/fse.rs`
- **Root Cause**: `HuffmanDecoder::decode` (`O0`) checked bit-buffer refills per symbol; `ContextualHuffmanEncoder`/`Decoder` (`O1`/`O2`) hashed `context` in `std::collections::HashMap<u32, usize>` (SipHash-1-3) on every byte and walked boxed `HuffmanNode` pointers 1 bit at a time; `Rans64Decoder<ParallelX4>::decode_parallel` decoded the 4 streams sequentially (`for stream_idx in 0..4`) instead of in lockstep; `fse_decompress` used 3 separate fields per table entry.
- **Optimization**:
  - `E4(c)`: Added a 12-bit (`4096`-entry) flat primary LUT `(symbol: u8, length: u8)` + 64-bit MSB bit-container in `HuffmanDecoder` (`O0`) and a 64-bit bit-accumulator in `HuffmanEncoder::encode`; replaced `ContextualHuffmanEncoder`/`Decoder`'s `HashMap` and pointer-tree walk with flat `context_map: Vec<u16>` (`256` entries for `O1`, `65,536` entries for `O2`), contiguous `encode_lut: Vec<u32>` (`len << 24 | code`), and flat 11-bit (`2048`-entry) per-context decode LUTs (`u16` packing `len << 8 | sym`).
  - `E4(d)`: Rewrote `Rans64Decoder<ParallelX4>::decode_parallel` to advance all 4 rANS states in lockstep over a packed 8-byte `RansFastDecodeEntry { freq: u16, cum_freq: u16, symbol: u8 }` table (`4096` entries = `32 KiB` L1D) with 32-bit bulk renormalization, and packed `FseDecompressEntry` into 8 bytes (`new_state_base: u32, symbol: u8, nb_bits: u8`).
- **Measured Result (`competitor_bench`)**:
  - `entropy/huffman_o0/{encode_64kib,decode_64kib}`: encode **`3.934 -> 2.359 ns/byte`** (`-43.1%`), decode **`7.116 -> 3.509 ns/byte`** (**`2.03x` faster**).

  - `entropy/huffman_o2/{encode_64kib,decode_64kib}`: encode **`54.539 -> 4.220 ns/byte`** (**`12.92x` faster**), decode **`39.166 -> 8.287 ns/byte`** (**`4.73x` faster**).
  - `entropy/fse/{encode_64kib,decode_64kib}`: encode **`6.166 -> 3.926 ns/byte`** (`-36.3%`), decode **`7.088 -> 4.193 ns/byte`** (`-40.5%`).
  - `entropy/rans64_x1/{encode_64kib,decode_64kib}`: encode **`5.233 -> 3.864 ns/byte`**, decode **`8.877 -> 4.693 ns/byte`** (`-46.8%`).
  - `entropy/rans64_x4/{encode_64kib,decode_64kib}`: encode **`5.888 -> 3.720 ns/byte`**, decode **`6.600 -> 2.493 ns/byte`** (**`2.65x` faster**).

### 3.8 `E3.7` — SSSE3 Quad Encode/Decode & Fused Prefix-Sum in `StreamVByte` and `GroupVarint` (`5bb8bc1`)
- **Files**: `src/compression/stream_vbyte.rs`
- **Root Cause**: `StreamVByte::encode_deltas` allocated a temporary `deltas: Vec<u32>` (`400 KiB`) and called `data.extend_from_slice(&v.to_le_bytes()[..len])` per integer; `StreamVByte::decode_deltas` performed a separate second pass over the output slice; `GroupVarint::encode` and `GroupVarint::decode_into` processed integers one at a time in scalar code.
- **Optimization**: Added an SSSE3 quad encoder (`_mm_Shuffle_epi8` + `_mm_min_epu8`/`_mm_movemask_epi8` control-byte computation with fused SIMD delta computation `_mm_sub_epi32(v, prev)`) and fused SIMD prefix-sum integration (`decode_deltas_into`) to `StreamVByte`, and wired `GroupVarint::encode_deltas` / `GroupVarint::decode_deltas` to the same SSSE3 `ENCODE_SHUFFLE_TABLE` / `SHUFFLE_TABLE` (`_mm_shuffle_epi8`).
- **Measured Result**:

  - `int_codecs/group_varint/decode_deltas`: **`9.654 -> 0.795 ns/int`** (**`12.14x` faster**).

### 3.9 `E4(a)` / `E3.8` — Cache-Conscious MSB+L2 LSD Radix Sort & 4-Bank AVX-512 Counting (`568e65b`)
- **Files**: `src/algorithms/radix_sort/lsd.rs`
- **Root Cause**: `RadixSort::sort_u32_sequential` and `sort_u64_sequential` performed 8 or 16 full-DRAM passes over `10,000,000` elements and allocated/faulted a fresh `80 MiB` `temp` vector on every call (`20,164` minor page faults per call); `KeyValueRadixSort::sort_by_key` allocated `160 MiB` `KVPair` + `160 MiB` scratch + `80 MiB` `targets` (`56.0 B/elem`) and chased random DRAM cycles.
